# Komprehension

A Kotlin compiler plugin that brings Scala-style for-comprehensions to Kotlin.

> **Status: the MVP works.** The rewrite and its seven diagnostics run on JVM and JS, and the
> [`sample`](sample) build exercises the whole thing through the Gradle plugin. Not published to a
> repository yet.

## What it looks like

```kotlin
val result = comprehend {
    val (name, subjects) = from(scores)
    val eng = subjects["English"].bind()
    val math = from(subjects["Math"])

    where(eng >= 70)

    name to (eng + math)
}
```

The plugin rewrites the block into nested `flatMap` calls, so the code above is equivalent to a
hand-written chain but reads as a flat sequence of bindings.

- `from(source)` and `source.bind()` are the same generator operation — use whichever reads better.
- Supported sources: `Iterable`, `Sequence`, `Array`, `Map` (binds `Pair<K, V>`) and nullable values.
  A `null` source contributes no elements.
- `where(condition)` drops the current branch.
- The last expression of the block is the result, and `comprehend` always returns `List<R>`.

Scala's `for` lets the first generator decide the result type; this one does not. That is what lets a
`Map`, a nullable and an `Iterable` sit in the same block: if the first generator decided, a block
starting from a nullable would have to produce `R?`, and there would be no answer for what an inner
`List` generator returning two elements should mean. Always `List<R>` keeps the mixing well defined.

The DSL is declared as ordinary Kotlin, so type inference and code completion work without any IDE plugin.

### What you cannot write inside the block

The rewrite moves the statements after a generator into a new lambda, so anything that would not
survive that move is a compile error rather than a surprise at run time. Three rules cover it.

1. A generator is the right-hand side of a `val`, or a statement on its own. `val a = from(xs) + 1`
   and `where(a.bind() > 3)` do not qualify — split them into two lines. This is the same restriction
   Scala puts on `<-`, and for the same reason: the rest of the block has to be separable.
2. The block's `this` cannot be used as a value. It disappears in the rewrite, so anything holding on
   to it would point at nothing.
3. No early `return`. There is nothing to return from once the lambda is gone, so a
   `return@comprehend` that is not the last statement — inside an `if`, say — is rejected. Written as
   the last statement it is accepted, because that is the result expression spelled out.

Sources that would otherwise bind as a single element are rejected too, so `from(intArrayOf(1, 2))`
tells you to convert first rather than quietly binding the whole array.

## Using it

Not published to the Gradle Plugin Portal or Maven Central yet, so there is no version to depend on.
To use it today, point your build at a local checkout:

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        mavenCentral()
        gradlePluginPortal()
    }
    includeBuild("../komprehension")
}

// Again outside pluginManagement, so the compiler plugin and runtime coordinates resolve too.
includeBuild("../komprehension")
```

```kotlin
// build.gradle.kts
plugins {
    kotlin("jvm") version "2.4.20"
    id("com.jsoizo.komprehension")
}
```

That is the whole setup — no dependency on the runtime, because the Gradle plugin adds it.

[`sample`](sample) is exactly this, wired to the checkout it sits in:

```console
cd sample && ../gradlew run
```

## Building

```console
./gradlew build
```

If `:kotlinNpmInstall` fails over a `packageManager` mismatch, the cause is a `package.json` in a
directory above this repository; `gradle.properties` already opts out of yarn to avoid it.

## Tests

The [Kotlin compiler test framework][test-framework] is set up for this project. To add a test, drop a
`.kt` file into a [compiler-plugin/testData](compiler-plugin/testData) sub-directory: `testData/box` for
codegen tests that run the compiled code, `testData/diagnostics` for expected-error tests. Each file
becomes one JVM test and one JS test. Expectation files are generated on the first (failing) run. The
JUnit 5 test classes are regenerated by the `generateTests` Gradle task, which also runs automatically
before `compileTestKotlin`.

A diagnostics test marks the error it expects inline:

```kotlin
val p = listOf(1).map { <!KOMPREHENSION_GENERATOR_IN_UNSUPPORTED_POSITION!>from(listOf(2))<!> }
```

The marker has to cover the same source range the diagnostic is reported on. Add
`// RENDER_IR_DIAGNOSTICS_FULL_TEXT` to the file and run once to get every diagnostic with its
line and column written to a `.ir.diag.txt` beside it.

Installing the [Kotlin Compiler DevKit][test-plugin] IntelliJ plugin — already configured in this
repository — makes running individual tests easier.
